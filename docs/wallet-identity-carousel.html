Build notes · wallet identity

Anonymous
by Design

How a payments wallet stores your phone number, and mints an account ID that gives away nothing — not your number, not your name, not even the order you signed up in.

DrutoPay · build notes01 / 06

The trap

Two ways to get this wrong

Attempt 1
Use the phone number as the account ID

PII everywhere The number then lands in every log line, every table join, every support screen, every analytics export. One leak exposes real people.

Attempt 2
Random digits, check the DB, retry on clash

Guessable random() is predictable — watch a few IDs, guess the next.

Race condition Two signups pass the “does it exist?” check at the same instant, then both insert.

The fix → split it into two separate jobs: make it unique, and separately, hide the sequence.

Step 1 · storing PII

The phone number, two ways

Input
raw phone   01XXXXXXXXX
Path A · to find you
HMAC-SHA256( secret pepper , phone )
phone_hash column  = 9f3a1c…c1

✓ same input → same output — you can look users up & block duplicates
✓ one-way — a stolen DB is not a list of phone numbers
✗ you can never read the number back from it

Path B · to reach you
AES-GCM · a fresh random IV per row
phone_enc column  = ░░░░░░

✓ decrypt with the key only when needed — OTP, verified support view
✗ different ciphertext every time — nothing can search on it
✗ useless to a thief without the key

Keep both. One column to find you, one to reach you.

Step 2 · the wallet number

Count first, then scramble

1 · database counter
Auto-increment column
1 2 3 …
atomic · unique · no lookup, no race
2 · offset
n + 1,000,000,000
so early IDs don’t sit at the edge of the range
3 · feed to
Feistel permutation ↓
Feistel permutation · 4 rounds · keyed
split n → L R  (17 bits each)
each round:   L, R  ←  R ,   L  XOR  F(R)
F(R) = HMAC-SHA256( key , round ‖ R )
after round 4:   join LR → n′
bijection — 1 input ↔ 1 output

Reversible with the key. No two inputs share an output — so the wallet number is unique by construction, never checked against the table.

4 · cycle-walk
n′ still bigger than 10 digits? run Feistel again. ~1.7 passes on average.
wallet_number
1→0675163119   2→0949555767   3→8942541949

Why it holds

A bijection can’t collide

counter 1 counter 2 counter 3 0675163119 0949555767 8942541949

one arrow in, one arrow out — always

✓ Every counter maps to one number, and every number to one counter.

✓ So two users physically cannot land on the same wallet number — with zero database checks.

✓ Consecutive in, scrambled out — the ID hides both signup order and total user count.

Compare
random + check has a race: two callers pass the check, then both insert the same value.
